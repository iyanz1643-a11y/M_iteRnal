# 13. AI 운영 설계

2026년 11월 14일에 정했다. 이 앱은 대표님과 AI가 만든다. AI가 무엇을 읽고, 어떤 순서로 돌고, 무엇에 연결되며, 누가 어떤 일을 맡는지를 네 장으로 정한다.

| 장 | 다루는 것 |
| --- | --- |
| 1. 컨텍스트 엔지니어링 | AI에게 무엇을 보여 주고 무엇을 보여 주지 않는가. 그것을 어떻게 낡지 않게 관리하는가 |
| 2. 루프 엔지니어링 | 개발, 결정, 품질, 앱 안 AI, 운영이 어떤 순서로 돌고 언제 멈추는가 |
| 3. 연결 엔지니어링 | 드라이브, 노션, 모바일 명함, Claude API 같은 바깥과 어떻게 잇고 끊겼을 때 어떻게 하는가 |
| 4. 파트별 에이전트 | 개발 일을 누가 맡고 어떻게 넘겨주는가 |

## 1. 컨텍스트 엔지니어링

### 1.1 개발 컨텍스트의 네 겹

작업이 여러 날에 걸치면 앞의 대화는 요약되거나 사라진다. 실제로 이 프로젝트의 대화도 한 번 요약됐다. 그래서 대화가 아니라 저장소가 기억하게 한다.

| 겹 | 파일 | 언제 읽는가 | 담는 것 |
| --- | --- | --- | --- |
| 항상 | `CLAUDE.md` | 작업을 시작할 때마다 | 지켜야 할 것, 어디에 무엇이 있는지, 용어, 개발 루프, 지금 어디까지 왔는지 |
| 필요할 때 | `docs/01` 에서 `docs/13` | 그 파트를 만들 때 | 기능, 구조, 디자인, 계산의 상세 |
| 원본 | `config/menu.yaml`, `schema/schema.sql`, `config/mapping/` | 코드가 직접 읽는다 | 메뉴와 권한, 테이블, 파일 매핑 |
| 상태 | `docs/10_개발계획.md` 의 파트별 상태와 결정 기록, `CLAUDE.md` 의 마지막 절 | 파트의 시작과 끝 | 된 것, 남은 것, 확정된 결정, 열린 결정 |

### 1.2 관리 규칙

1. **한 사실은 한 곳에만 적는다.** 다른 곳에서는 위치나 결정 ID 만 가리킨다. 열린 결정은 `docs/10` 7.2 한 곳에 있다.
2. **항상 읽는 글은 150줄 이하로 둔다.** 넘으면 문서로 내리고 한 줄만 남긴다.
3. **에이전트마다 읽을 것을 정한다.** `.claude/agents/` 의 각 파일에 읽는 문서와 손대는 파일을 적어, 필요한 것만 읽게 한다.
4. **결정은 날짜나 ID 와 함께 적는다.** 가정은 가정이라고 적는다.
5. **표로 뽑을 수 있는 것은 원본에서 뽑는다.** 화면 표는 `config/menu.yaml` 에서 만든다.
6. **실제 자료의 내용은 싣지 않는다.** 머리글, 건수, 값의 종류만 싣는다.
7. **파트가 끝나면 상태를 고친다.** `CLAUDE.md` 의 마지막 절과 `docs/10` 4장이다.

### 1.3 신선도 점검

규칙은 사람이 지키기 어렵다. 그래서 `scripts/check_context.py` 가 검사하고, `tests/test_context.py` 가 자동 시험에 넣는다. 올릴 때마다 돈다.

| 검사 | 실패하는 경우 |
| --- | --- |
| 화면과 메뉴 | `menu.yaml` 에서 새 화면이라고 한 주소가 `app/web` 에 없다. 또는 새 화면의 주소가 메뉴에 없다 |
| 화면 표 | `docs/11` 4.3 의 표가 `menu.yaml` 에서 다시 만든 표와 다르다 |
| 결정 ID | 다른 문서가 가리키는 결정 ID 가 `docs/10` 7.2 의 열린 결정에도 7.1 의 확정된 결정에도 없다. ID 가 겹치거나 7.1 과 7.2 에 함께 있다 |
| 상태 날짜 | `CLAUDE.md` 의 마지막 절에 갱신 날짜가 없다. 마지막 커밋보다 14일 넘게 오래되면 경고만 한다 |
| 개인정보 꼴 | 저장소의 글에 주민번호나 휴대폰 번호 꼴의 문자열이 있다 |
| 안내 글 길이 | `CLAUDE.md` 가 150줄을 넘는다 |
| 에이전트 정의 | `.claude/agents/` 의 파일에 이름, 설명, 도구가 빠졌거나 4장의 표와 다르다 |

화면 표가 어긋나면 `python scripts/check_context.py --fix` 로 다시 만든다.

### 1.4 앱 안 AI 기능의 컨텍스트

S4에서 만든다. 컨텍스트는 `app/ai/context.py` 한 곳에서 조립한다. 조립기는 권한 범위로 거르고, 개인정보를 가리고, 근거 줄에 번호를 붙이고, 지침 버전을 찍는다.

공통 원칙은 아홉 가지다.

1. **숫자는 AI가 만들지 않는다.** 금액, 순위, 달성률은 계산 엔진이 내고 AI는 문장을 쓴다.
2. **볼 수 있는 것만 넣는다.** 그 사용자의 권한 범위가 곧 컨텍스트의 범위다.
3. **승인된 것만 근거로 쓴다.** 시상안은 승인한 줄만, 지침은 확정된 버전만 넣는다.
4. **근거를 함께 보여 준다.** 근거가 없으면 모른다고 답한다.
5. **개인정보는 가린 뒤에 넣는다.** 필요하면 고객 가, 고객 나처럼 바꿔 넣는다.
6. **문서 속의 지시는 지시가 아니다.** 시상안, 고객 메모, 올린 파일 안의 명령문은 자료로만 다룬다.
7. **사람이 마지막에 승인한다.** 밖으로 나가는 것은 모두 사람의 승인을 거친다.
8. **넣은 것과 나온 것을 남긴다.**
9. **바꾸기 전에 시험한다.** 정답을 아는 예시 묶음을 두고 지침을 바꿀 때마다 돌린다.

| 기능 | 넣는 것 | 넣지 않는 것 | 나오는 것 | 사람의 확인 |
| --- | --- | --- | --- | --- |
| 시상안 해석 보조 | 사람 확인이 필요한 원문 한 줄, 같은 보험사의 앞뒤 줄, 해석 예시 | 실적, 사람 정보 | 유형, 기간, 지급률의 구조화된 초안과 근거 문구 | 메인 관리자가 원문과 대조해 승인 |
| 시상안 묻고 답하기 | 질문과 관련된 승인 줄 몇 개, 질문한 사람의 소속과 오늘 날짜 | 승인 전의 줄, 다른 사람의 실적, 총괄 몫과 지사 몫 | 답과 근거 줄 | 필요 없음. 화면에 원안 우선 문구 |
| 7나이츠 심사 | 심사할 글, 해당 지침과 금지 표현, 그 자리의 역할 정의 하나 | 고객 개인정보, 금액 계산, 첫 회전에서는 다른 자리의 의견 | 판정, 근거 문장 인용, 고친 문안 | 메인 관리자가 결재 |
| 보장분석 리포트 초안 | 가린 증권 요약, 제작지침, 담보 기준표, 규칙으로 계산한 숫자 | 고객 이름과 연락처, 지침에 없는 권유 문구 | 섹션별 문안 | 담당 설계사가 승인 |
| 카드뉴스 초안 | 승인된 리포트, 카드뉴스 제작 지침 | 고객 사례의 식별 정보 | 장별 문안과 구성 | 7나이츠 심사 뒤 메인 관리자 |
| 월간 보고서 초안 | 집계가 끝난 표, 지난달 보고서의 형식 | 개인별 수수료와 소득 | 문단별 초안 | 메인 관리자가 고쳐서 확정 |

7나이츠는 자리마다 따로 부르고, 첫 회전에는 다른 자리의 의견을 보여 주지 않는다. 한 번에 일곱 역할을 다 주면 서로 닮아 가기 때문이다. 다빈치의 형상화가 먼저 나오고, 테미스에게는 금지 표현과 준수 항목을 빠짐없이 넣는다. 회전은 세 번까지다.

묻고 답하기는 원장 전체를 넣지 않는다. 질문에서 보험사, 상품군, 기간을 뽑아 맞는 줄만 원문 그대로 번호를 붙여 넣는다. 상품을 권하는 답은 하지 않는다.

## 2. 루프 엔지니어링

루프마다 순서, 멈추는 조건, 재는 것을 둔다.

### 2.1 개발 루프

파트 하나를 이 순서로 돈다.

| 단계 | 하는 일 | 쓰는 것 |
| --- | --- | --- |
| 1. 읽기 | `CLAUDE.md`, 그 파트의 에이전트 정의, 에이전트가 정한 문서 | 1.1 의 네 겹 |
| 2. 계획 | 완료 기준과 막힌 결정을 확인하고 일을 나눈다 | `docs/10` 4장과 7.2 |
| 3. 만들기 | 에이전트가 맡은 파일만 고친다 | 4장의 표 |
| 4. 검증 | 자동 시험, 샘플 전체 실행, 브라우저 점검, 컨텍스트 점검. 검증은 만든 에이전트가 아니라 verifier 가 한다 | `pytest`, `run_demo.py`, `check_context.py` |
| 5. 기록 | 문서, 메뉴 상태, 결정 기록, 지금 어디까지 왔나 | docs-keeper |
| 6. 보고 | 된 것, 검증 결과, 남은 가정, 열린 결정을 한 번에 | 대표님 |

멈추는 조건은 세 가지다.
- 다섯 가지 검토 사항에 닿았다. 돈, 사람, 제도, 밖으로 나가는 것, 되돌리기 어려운 것이다.
- 같은 시험이 세 번 고쳐도 실패한다.
- 실제 자료가 필요한데 없다.

재는 것: 파트마다 시험 수, 검증에서 되돌아간 횟수, 남은 가정 수.

### 2.2 결정 루프

| 단계 | 하는 일 |
| --- | --- |
| 1 | 열린 결정을 `docs/10` 7.2 에 ID 와 필요한 스프린트를 붙여 적는다 |
| 2 | 그 스프린트 전에 질문 한 줄, 제안, 다른 선택지, 미루면 생기는 일의 네 줄로 여쭙는다 |
| 3 | 답이 없으면 제안대로 샘플 자료 안에서 진행하고 가정으로 표시한다 |
| 4 | 답이 오면 7.1 로 옮기고, 가정으로 만든 부분을 고치고, 시험을 다시 돌린다 |

실제 자료나 실제 사용자에게 닿는 일은 답을 받은 뒤에만 한다.

### 2.3 품질 루프

1. 오류를 찾으면 그 오류를 재현하는 시험을 먼저 쓴다.
2. 고친다.
3. 시험 전체를 다시 돌린다.

화면이 달라도 같은 사람의 같은 숫자는 같아야 한다. 11월 14일에 부문 순위와 홈의 인정보험료가 달랐던 일에서 배운 것이다. 그래서 숫자를 서로 대조하는 시험을 둔다.

### 2.4 앱 안 AI 루프

S4에서 만든다.

| 단계 | 하는 일 |
| --- | --- |
| 1. 조립 | 1.4 의 조립기가 컨텍스트를 만든다 |
| 2. 생성 | Claude API 를 부른다 |
| 3. 자동 점검 | 금지 표현이 있는지, 출력의 숫자가 모두 입력에 있는지 본다 |
| 4. 심사 | 밖으로 나가는 글은 7나이츠가 심사한다. 최대 3회전 |
| 5. 승인 | 사람이 승인하거나 고친다 |
| 6. 기록 | 입력의 해시, 지침 버전, 출력, 사람이 고친 문안 |
| 7. 평가 | 정답 예시 묶음으로 회귀 평가 |
| 8. 개선 | 반려 사유와 고친 문안을 보고 지침을 고치고 버전을 올린다 |

멈추는 조건은 네 가지다. 3회전을 넘었을 때, 근거가 없을 때, 월 비용 한도에 닿았을 때(D-26), 자동 점검에서 숫자가 맞지 않을 때다.

재는 것은 승인율, 사람이 고친 비율, 반려 사유별 건수다.

### 2.5 운영 루프

앱이 쓰일 때의 월간 순환이다. 시상안 적재, 해석, 승인, 게시, 계약 적재, 달성 현황, 마감, 확정, 공유로 돈다. 상세는 `docs/09` 3.1에 있다. 재는 것은 `docs/09` 1장의 성공 기준이다.

## 3. 연결 엔지니어링

### 3.1 두 종류의 연결

| 종류 | 쓰는 쪽 | 예 | 키 |
| --- | --- | --- | --- |
| 개발 연결 | 개발하는 AI | 드라이브, 시트, 노션, 기획안 문서, GitHub 커넥터 | 대표님 계정의 커넥터 |
| 운영 연결 | 앱 | 드라이브 자동 가져오기, 노션, 모바일 명함, Claude API, 카카오 | 앱 전용 키. 환경 변수로만 둔다 |

### 3.2 운영 연결 목록

| 연결 | 방향 | 쓰임 | 키 | 스프린트 | 실패하면 |

| 구글 드라이브와 시트 | 들어옴 | 지정 폴더 자동 가져오기 | 서비스 계정. 읽기 전용 | S3 | 파일 올리기로 |

| 카카오 알림톡 | 나감 | 알림 | 발신 프로필 | D-10 이후 | 앱 안 알림 |

### 3.3 모바일 명함 연동

명함 사이트의 코드를 읽고 정했다. 명함 사이트에는 이미 다음 기능이 있다.

- 명함 신청: 주소 이름, 이름, 연락처, 명함 화면과 미리보기 그림
- 본부의 승인, 반려, 내리기
- 공개 상태 조회
- 관리자 목록
- 교육 수료 코드 발급: 과정, 수료월, 명단

관리자 기능은 관리자 키 머리글로 연다. 배지는 명함 그림 안에 그려져 있어서 서버에서 지울 수 없다.

| 단계 | 연동 | 방향 | 스프린트 |
| --- | --- | --- | --- |
| 1차 | 설계사와 명함 주소를 잇는 표. 내 명함 화면에 공개, 대기, 반려 상태와 링크. 승인 대기 목록을 앱에서 본다 | 명함에서 앱으로. 읽기 | S2 |
| 2차 | 명함 승인과 반려를 앱에서 한다. 교육 파트의 수료 기록으로 수료 코드 발급을 앱이 요청한다. 코드 원문은 저장하지 않고 일련번호와 해시만 둔다 | 앱에서 명함으로 | S2. 수료 코드는 교육 파트와 함께 |
| 3차 | 인증과 수상 배지의 자격과 유효기간을 앱이 판정한다. 만료 예정 목록과 재발급 안내를 낸다. 해촉자의 명함은 내리기 후보로 띄우고, 메인 관리자가 승인하면 내린다 | 앱에서 명함으로 | S3 |

- 연동 키(`CARD_ADMIN_KEY`)는 환경 변수로만 둔다. 키 발급과 주소 매핑 방법은 D-28 이다.
- 승인, 반려, 수료 코드 발급, 내리기는 밖으로 나가는 일이라 앱에서 사람이 확인한 뒤에 보낸다. 누가 무엇을 하는지는 D-44 다.
- 앱이 명함 사이트에 쓰는 일은 쓰기 스위치 `CARD_SITE_WRITE` 가 켜져 있을 때만 한다. 스위치는 `11_개발구조.md` 6장에 있다.
- 명함 사이트의 씨앗 자료에는 실명이 있다. 출력하거나 이 저장소로 옮기지 않는다.
- 프로모션과 부문 시상의 수상자 카드에서도 명함 주소를 링크로 쓴다.

### 3.4 연결 원칙

1. **어댑터 한 곳.** 앱의 운영 연결은 `app/connect/` 에 모은다. 흐름은 가져오기, `data/raw` 에 원본과 해시 보관, 기존 적재기의 순서다.
2. **같은 파일은 두 번 넣지 않는다.** `import_batch.file_hash` 와 `received_via` 를 쓴다.
3. **시간 제한과 재시도를 둔다.** 연결이 실패해도 월 마감은 멈추지 않는다.
4. **키는 환경 변수로만, 처음엔 읽기 전용으로.** 쓰기가 필요하면 그때 범위를 넓힌다.
5. **연결 상태를 보여 준다.** 메인 관리자 화면에 연결마다 마지막 성공 시각과 실패 사유를 둔다.
6. **파일 직접 올리기는 없애지 않는다.**

11월 13일에 개발 연결이 한동안 끊겼다. 드라이브 내려받기의 10MB 제한과 60초 시간 초과도 있었다. 그날 이 대화에 파일을 직접 첨부하는 길과 구글 시트로 셀을 읽는 길로 우회했다.

### 3.5 연결 상태와 명함 연결의 저장

S1 에 연결 상태와 명함 연결을 앱 DB 의 표 세 개로 옮겼다. 표의 정의는 `schema/schema.sql` 의 운영 연결 묶음이다. 표를 쓰는 DB 는 `11_개발구조.md` 6장의 `CONNECT_STATE_DB` 로 정한다.

| 표 | 담는 것 | 쓰는 곳 |
| --- | --- | --- |
| `connection_state` | 연결마다 마지막 시도, 마지막 성공 시각, 마지막 실패 사유, 연속 실패 횟수 | `app/connect/state.py` |
| `connection_watch` | 폴더 감시가 이미 끝낸 파일의 크기, 바뀐 시각, 해시, 결과 | `app/connect/state.py` |
| `card_link` | 설계사와 명함 주소의 이음. 끊을 때는 지우지 않고 끊은 시각을 채운다 | `app/connect/card_link.py` |

- 예전 상태 파일 `data/state/connections.json` 은 `python -m app.connect migrate-state` 로 내용을 표에 옮긴다. 처음 쓸 때도 한 번 옮긴다. 원본 JSON 파일은 지우지 않고 그 자리에 둔다. 표에 이미 있는 줄은 표의 것을 둔다.
- 명함 연결은 제안과 확정을 나눈다. 이름 대조 제안은 표에 넣지 않고 확인 화면에만 보인다. 확정과 끊기는 메인 관리자만 하고 변경 기록에 남긴다.
- 세 표에는 사람 이름, 연락처, 금액, 키를 넣지 않는다.
- `data/raw` 에 보관한 사원현황 원본은 지우지 않는다. 보관 기준은 D-43 이다.

| 누구 | 하는 일 |
| --- | --- |
| 대표님 | 다섯 가지 검토 사항의 결정과 결재 |
| AI 총괄 | 메인 작업. 개발 루프를 돌리고, 파트를 에이전트에게 나눠 맡기고, 결과를 합쳐 보고한다. 에이전트 파일은 두지 않는다 |
| 에이전트 9개 | 아래 표. `.claude/agents/` 에 정의한다 |

### 4.2 에이전트

| 에이전트 | 이름 | 맡는 파트 | 손대는 곳 | 하지 않는 것 |
| --- | --- | --- | --- | --- |
| data-loader | 데이터 적재 | B | `app/loader`, `config/mapping`, 원본 쪽 스키마 | 실제 자료의 이름과 금액 출력 |
| calc-engine | 계산 | C, D, E, G, I 의 계산 | `app/engine`, 계산 쪽 스키마 | 화면 |
| web-screen | 화면과 랜딩 | C, D, E, F, G, I, J 의 화면, 랜딩 두 가지, 휴대폰 홈 화면 추가 | `app/web` 의 화면, 템플릿, 스타일, `menu.yaml` 상태 | guard 우회, 계산 로직, 심사 없이 랜딩 문구 게시 |
| auth-org | 기반과 권한 | A, H | `app/web/auth.py`, 조직과 계정, 권한 시험 | 범위 검사 완화 |
| platform | 백엔드와 인프라 | 라우터 분리, CSRF, DB 전환, 작업 워커, 저장소, 배포, 백업, 관측 | `app/web/main.py` 의 골격, 마이그레이션, 배포 설정, CI | 승인 없는 운영 배포, 비밀 값을 저장소에 넣기 |
| connector | 연결 | 3장의 연결, B 의 수집, 명함 연동 | `app/connect`, 연결 설정 문서 | 키를 코드나 문서에 적기 |
| ai-features | 앱 안 AI | 1.4 의 기능, K 의 7나이츠 | `app/ai`, 지침과 예시 묶음 | 숫자 생성, 승인 없는 외부 발신 |
| verifier | 검증 | 모든 파트 | `tests` 만 쓴다. 나머지는 읽고 실행만 | 기능 코드 고치기 |
| docs-keeper | 문서와 컨텍스트 | 모든 파트의 기록 | `docs`, `CLAUDE.md`, 결정 기록, `scripts/check_context.py` | 결정을 대신 내리기 |

### 4.3 협업 규칙

1. **만든 쪽과 검증하는 쪽을 나눈다.** 모든 파트는 verifier 가 검증한다.
2. **스키마는 덧붙이기만 한다.** `schema/schema.sql` 은 한 번에 한 에이전트만 고친다. 합치는 일은 총괄이 한다.
3. **파일이 겹치지 않는 에이전트끼리만 나란히 돈다.** 겹치면 차례로 돈다.
4. **넘겨줄 것을 정해 둔다.** 바꾼 파일, 시험 결과, 남은 가정, 열린 결정이다. 총괄이 받아 docs-keeper 에게 넘긴다.
5. **다섯 가지 검토 사항에 닿으면 에이전트는 멈추고 총괄에게 돌려준다.** 대표님께 여쭙는 것은 총괄이 한다.

### 4.4 7나이츠와의 구분

7나이츠는 앱 안의 심사 역할이고 개발 에이전트가 아니다. 다만 설계사와 고객에게 나가는 화면 문구와 랜딩 문구는 S4부터 7나이츠 심사를 거친다.
